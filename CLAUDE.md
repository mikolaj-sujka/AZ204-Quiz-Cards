# AZ-204 Quiz Cards — project guide for Claude Code

## Purpose

This is a personal, local-first study app for **Exam AZ-204: Developing Solutions
for Microsoft Azure**. It is not a product — it exists to help the repo owner pass
the AZ-204 exam by reading focused reference articles per service/concept and
then testing themselves with subchapter/mock exams, organized around the exact
chapter/subchapter structure of the official exam.

Everything in this repo should be judged against one question: **does this change
help the user learn AZ-204 content faster and more reliably, and does it stay
accurate to the current official exam scope?**

## Where content comes from

There are three content sources, and they are treated differently:

1. **Original content** — `src/data/az204-content.json`
   - Chapter/subchapter structure, weights, study notes: hand-authored to mirror
     the official Microsoft Learn AZ-204 study guide structure.
   - A small set of original questions (`content.questions`).

2. **Imported source-quiz bank** — `src/data/source-quiz.generated.json`
   - Machine-generated by `scripts/importSourceQuiz.mjs` from the public repo
     https://github.com/arvigeus/AZ-204 (markdown question files under
     `Questions/`), licensed CNAL (non-commercial, attribution-required — see
     `NOTICE.md`). Do not relicense or strip attribution from this content.
   - Every imported item is mapped to an AZ-204 chapter/subchapter and to one or
     more official `https://learn.microsoft.com/...` source URLs via the
     `topicMap` in `importSourceQuiz.mjs`.
   - Only closed (multiple-choice) items are imported — the generator drops
     open/code-only items at generation time, since they have no exam use.
   - **This file is generated, not hand-edited.** If an item needs a wording fix,
     a factual correction, or should be excluded (duplicate, off-scope,
     unfixable), the fix belongs in `importSourceQuiz.mjs` (`correctionFor` for
     factual patches, an exclusion list for removals) so that re-running
     `npm run import:source-quiz` reproduces the corrected/curated state instead
     of silently reintroducing the problem. Only patch the generated JSON
     directly as a stopgap when you also update the generator in the same
     change.

3. **Articles** — `src/data/articles.json`
   - Original reference material, one article per exam-relevant service/concept
     (e.g. "Azure Container Registry", "Deployment slots & traffic routing"),
     grouped under the same chapter/subchapter structure as the rest of the
     app. Not derived from the arvigeus quiz — researched and written directly
     against current Microsoft Learn documentation.
   - **Hand-authored/curated, not generated** — unlike the source-quiz bank,
     there's no regeneration script; edit `articles.json` directly, and keep
     `sourceUrls` pointing at whatever `learn.microsoft.com` page was actually
     checked for that article's claims. Use the `verify-az204-content` skill
     before adding or editing an article.

Regenerating the source-quiz bank calls the GitHub API and requires network
access; treat it as a deliberate, reviewed action (diff the result) rather than
something to run casually.

## What counts as "correct"

**Microsoft Learn is the single source of truth**, specifically:

- https://learn.microsoft.com/en-us/credentials/certifications/azure-developer/
- https://learn.microsoft.com/en-us/credentials/certifications/resources/study-guides/az-204
- https://learn.microsoft.com/en-us/training/courses/az-204t00
- and the specific service-level Learn pages referenced per topic in `topicMap`.

A content item is only allowed to carry `"auditStatus": "verified"` if:

- Its `sourceUrls` are official `learn.microsoft.com` URLs relevant to the claim
  (enforced by `scripts/validateContent.mjs`, which fails the build if any
  active item lacks Microsoft Learn sourcing).
- The factual claim in the prompt/answer/explanation matches what Microsoft
  Learn currently documents — not what the upstream source-quiz repo originally
  said. The upstream repo has known errors; several are already corrected via
  `correctionFor(...)` in `importSourceQuiz.mjs` (e.g. Cosmos DB name-length
  limits, composite index ordering). When Microsoft Learn and the upstream quiz
  disagree, Microsoft Learn wins and the item gets a `correctionNotes` entry
  explaining what was fixed and why.
- It is in current exam scope. AZ-204 retires **31 July 2026**; the active
  scope is "skills measured as of 14 January 2026" (see the retirement banner
  in `Header()` in `src/App.tsx`). Content testing retired/out-of-scope
  services should be flagged, not silently kept just because it once shipped.

If a claim can't be verified against a current Microsoft Learn page, it should
not be marked `verified` — flag it instead of guessing.

## Architecture quick map

- `src/domain/content.ts` — types + all content-shaping logic (combining the
  original and imported banks, filtering by chapter/subchapter, weighted mock
  exam selection). Read this first to understand how the two data files
  combine.
- `src/domain/progress.ts` — `localStorage`-backed article read-state and exam
  attempt history. Pure functions, easy to unit test.
- `src/domain/scoring.ts` — answer comparison/scoring for exams.
- `src/App.tsx` — the entire UI (dashboard, articles, exam, audit views).
- `scripts/validateContent.mjs` — the correctness gate; run it after touching
  any data file (including `articles.json`).
- `scripts/importSourceQuiz.mjs` — the only place that should add, correct, or
  exclude imported source-quiz items.
- `scripts/checkExamUpdates.mjs` — periodic watcher that diffs official
  Microsoft Learn AZ-204 pages against a snapshot and opens a PR when the exam
  scope changes; see `.github/workflows/exam-watch.yml`.

## Before calling a change done

Run, in order:

```bash
npm run validate:content
npm run typecheck
npm run test
```

`npm run test:e2e` and a manual pass in the browser are worth it for anything
touching `src/App.tsx` UI behavior (articles flow, exam flow) since those are
the two things this app is actually used for daily.

If `package.json`/`package-lock.json` change, also run `npm ci` (not just
`npm install`) before pushing — CI uses `npm ci`, which is strict about the
lockfile matching exactly. CI pins npm to `10.9.8` (see the "Pin npm version"
step in the workflows); regenerating the lockfile with a different npm major
version can produce a lockfile that's only consistent for that other npm
version, causing `npm ci` to fail in CI with a "Missing: ..." error even
though `npm install` succeeds locally. If that happens, regenerate with
`npx npm@10.9.8 install` to match CI exactly.
